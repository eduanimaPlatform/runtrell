# Workspace・Artifact・検証・context（data schema 3）

2aの未実装WorkspaceStore/ArtifactStoreを、actor（tenant/Run/Agent）に結び付くAccessで置き換える。RunStore/OperationStore/BudgetAuthority/Schedulerのtraitは変更しない。所有者以外は既定拒否。子Runの共有は信頼済みhostがRunRecord.parentを照合して版付きgrantを発行する。共有は読取/更新を分け、更新後の再共有を必要とする。

namespaceごとにmanifest revisionをCASし、一括write/delete/exact-replaceは全件を検査して1回commitする。ファイルrevisionはnamespace commit revisionを使いABAを防ぐ。snapshot hashはnamespace・revision・ソート済みfile manifestへ結び付く。copyの入力snapshotを固定し、回収はそのsnapshotと現行manifestの一致を条件とする。削除も明示Changeとして回収する。無関係なnamespaceは独立する。

保存受付はStagedでありread/finalize対象外。commit成功のみSaved。in-memoryはprocess内保証。local FSはrootのdirectory FDからNOFOLLOWで各componentを開き、固定名状態fileをrename/fsyncで更新する。symlink/hardlink/非regular fileを拒否。namespace単位のOS lockを持ち、複数instance/process間でもCASする。論理pathをOS pathに使わない。root設定自体もcomponentごとにNOFOLLOW。容量/保持/削除はWorkspace/中間/最終Artifact/checkpoint/logを別policyで設定する。期限到達は削除許可の条件で、自動消去完了ではない。

Artifactは保存済み不変blob・manifest・生成元を持つ。外部参照と範囲read/打切り表示でcontextへ全文を入れない。Validatorはhostが登録するRust実装で、Workspace内の実行fileを検証器としてロードしない。診断はcode/severity/artifact/file/field/span/cause/hint。検証証跡は対象hash・manifest・basis/config/validator版へ結び付けてstoreに保存する。Finalizerは現在のsnapshotと信頼済みreceipt集合を同じnamespace transactionで検査し安定completion IDを保存する。構造化判断にも同じTargetを用い、ファイルを要求しない。業務ownerへの反映とRun成功は2aの別barrier。

contextは開始revision/high-waterを固定し、構造化した目的・制約・未完了操作・Artifact/出所を保持する。圧縮は完全な成功応答のみCAS保存。途中のappendでrevisionが進めば拒否し、元履歴を保持する。要約要求はRuntime.dispatchのCompactionとして予約・記録する。promptは自社文面。tool catalogはモデルに提示したdescriptor全体のdigestを固定、現行実装と一致しなければ拒否し、現在policyも毎回照合する。toolは既定直列、競合範囲と版CASを宣言する。

## 初期backendの具体的な制約

論理pathはportable ASCII（英大小文字・数字・`._-/`）を受け付け、空component・`.`・`..`・絶対path・backslashを拒否する。manifest内のfile/親directoryについて大小文字だけ異なる別名も拒否し、`Cargo.toml`等の普通の大文字名は利用できる。同一fileへの複数exact-replaceは各digestを開始内容へ照合し、staging上で順番に置換して1commitする。

local rootはhost専有の既存directoryを設定する。root自体にもsymlinkを許さないので、macOSの`/var`経由はhostが実pathを選ぶ。論理fileはOSのpathへ直接露出せず、将来のcopy/mountの実体化はExecutionBackendの責務。保存状態はnamespace単位のJSONであり、大きいblobもこの初期backendでは同じ状態file内に保持する。範囲APIの返却は有限だがdiskの部分read最適化やthroughput/SLOを保証しない。host processのSIGKILL中に残る未commitの`stage-*`は正本として読まない。namespace lock取得時に孤立した一時stateファイルを回収する。電源断試験は未提供であり、保存済みとの報告には含めない。

retentionは2a Clockと同じUnix millisecond。class cleanupは保持中staging・保持中/確定済みblobが残ればPending。確定済みblobはFinal policyも適用した個別deleteを使う。Workspace/Checkpointの全体削除にはowner、期待revision、明示retain境界が必要。Run終端を自動削除許可にしない。context圧縮は明示`Runtime::compact_context`を提供し、自動起動閾値は固定しない。hostは構造化contractの投入と圧縮後contextのモデル入力への採用を決める。2a protocol checkpointの内部履歴そのものを置換する実装ではない。

## Backend契約の拡張（rt-3c）

標準ツールはWorkspaceStore/ArtifactStoreと証跡用traitを要求し、具体backendを要求しない。Savedは不変blobとmanifestの照合後、Finalizedは現在版・hash・保存済み証跡を照合したcommit markerの保存後にだけ公開する。blob保存、manifest公開、証跡保存、確定marker、Run終端は順序付きの別境界とし、分散transactionを要求しない。adapterは各境界をCASし、応答喪失後は同一IDで再照会する。stagingは所有namespaceと期限を持ち、未確定データだけを所有者が期限後に回収する。確定済みデータをstaging GCの対象にしてはならない。

JSON SchemaはDraft 2020-12を共通実装で検証する。formatを検証し未知formatを拒否、参照は文書内fragmentのみ。未知keyword、別draft、外部参照、未対応vocabularyは構成エラーとする。診断のpathはinstance JSON Pointer、schema_pathはschema JSON Pointerを表す。業務基準・修正可否の具体的なcodeはhostが供給する。


namespaceの保存互換性識別子は`schema=3`。実装commitとは独立して照合する。未知/旧形式は拒否し、暗黙の移行や旧経路は持たない。ControlStoreのwire/checkpoint schema=1と、checkpoint内のrepair schema=1は別の識別子である。StagedのID・所有者・bytes・class・期限をnamespaceへ保存し、`staged`で再取得、`save`で同一IDの保存を再試行する。`cleanup_staging`は期限到達した未公開データだけを所有者権限で削除する。Local一時stateファイルの寿命はtransaction lockに結び付き、次のlock取得者が孤立ファイルを回収する。Saved/Finalizedの正本markerには触れない。

`NamespaceBackend`の参照実装経路はblobも含むnamespace全体を一つのopaque JSONとしてCASするため、大容量の分離object store最適化はしない。blobを分離するadapterはWorkspaceStore/ArtifactStore/StandardToolStore/EvidenceStoreを直接実装できる。その場合、先に所有付きstaging/blobを保存し、hashを確認してから版付きmanifestへ参照をCAS公開し、証跡保存後に確定markerをCAS公開する。各段階の安定IDで再開し、公開済みmarkerから参照されるblobをGCしない。複数サービスの原子commitを仮定しない。共通suiteの停止/部分upload試験はこの契約のfake検証であり、実サービスの耐久性や性能はadapter側の受入試験を要する。

## 安定IDのraw-byte保存（rt-3f、data schema 3）

`ArtifactStore::stage_named`はhost指定の`ArtifactSpec`（namespace内の非空ID、media type、DataClass）と任意のraw bytesを受け、`save`でSavedを公開する。WorkspaceStoreとの組合せはStandardToolStoreで利用できる。IDはOS pathとして扱わない。同ID・同bytes・同media type・同classのstage再試行は元のstagingを返し、save再試行は元のArtifactRefを返す。bytesまたはmetadataが異なればConflict。再試行で期限・manifest・revisionは更新しない。保存済みIDへのstageも可能で、続くsaveは既存Artifactを返す。ランダムIDのstage/putはapplication/octet-stream、store_outputはapplication/jsonを使う。

安定IDはtenant/Run/Agentのnamespaceに属する。他namespaceから元namespaceのIDをstage/save/readする権限は付与しない。同じ文字列を自分のnamespaceで使うことは独立したArtifactであり、他Runの参照にはならない。stage_namedは所有者専用。既存の明示共有によるread契約は維持する。

stage応答後・save応答後のclient停止と再openでは永続状態から同じIDを再開する。外部CASの応答喪失でも同IDを再送できる。保存完了と耐久性の範囲は既存backend契約どおり。未公開stagingの期限後GC・明示削除後にはIDの記録を保持しないため、永久の重複排除ではない。Memoryの再openは共有状態の再接続でありprocess耐久ではない。Local/fake外部storeの共通suiteはclient再openを試す。追加のLocal子process試験はstage/save応答直後にデストラクタなしでprocessを終了して別processから復元する。SIGKILL・電源断の試験ではない。PostgreSQL adapterは制御台帳専用でArtifact保存を提供しない。

media typeをStaged/ArtifactRefへ必須保存するためnamespace schemaを3へ更新する。旧schemaの暗黙移行・互換fallbackは追加しない。control/checkpointのschemaは変更しない。

## rt-5：コード実行への限定copy

ExecutionToolの入力`files`は正確な論理pathの集合であり、未指定fileを読取ったり実行環境へ渡したりしない。`ExecutionRequest.workspace_base`に全WorkspaceのCAS基準、`input`に選択fileのmanifest、`input_files`にそのbytesを固定する。namespace・revision・選択manifestの所属・各fileのhash/bytesを検査し、読取前後に全snapshotを照合する。全Workspaceを渡す低水準freeze_workspaceはworkspace_baseを必要とせず、input自体がCAS基準になる。旧保存形式の読替えではない。

成果物は明示`outputs`だけを受理し、backendの予期しないpathは保存しない。停止後のbounded出力は先に安定IDのIntermediate Artifactへ保存し、全WorkspaceのCASを用いてmergeする。競合・取消・権限失効では`saved=false`と`save_error`を返し、Artifactと実行台帳のcopyを保持する。`saved=true`のときだけ保存済みWorkspaceの版とfile manifestを返す。mergeの成功からoperation結果記録までのWorker停止は再実行せず、元CASでの再保存が競合すれば保存状態を保守的に未確認と報告する。保存済み内容を巻き戻さない。Artifact retentionはhostのStoragePolicyに従う。
